## 速率限制

公益站对 API 调用频率有上限，防止单个用户占用过多资源。

| 限制类型 | 说明 |
|---------|------|
| 每分钟请求数 | 平台根据负载动态设定，通常每分钟几十次 |
| 并发请求数 | 同一令牌同时进行的请求数有上限 |
| 每日额度 | 每个用户每天有 Token 消耗上限，次日重置 |

<Callout type="warn" title="429 错误">
  如果你收到 `429 Too Many Requests` 错误，说明触发了速率限制。请降低调用频率，等待一段时间后重试。
</Callout>

### 如何避免触发限流

<Steps>
  <Step title="控制请求频率">
    在代码中加入合理的请求间隔，避免短时间内密集调用。
    建议单用户每秒不超过 2-3 次请求。
  </Step>
  <Step title="合并请求">
    如果有多个独立调用，考虑合并到一次多轮对话中，
    减少 API 调用次数。
  </Step>
  <Step title="使用缓存">
    对于相同输入的请求，在本地缓存结果，
    避免重复调用。
  </Step>
  <Step title="实现指数退避">
    遇到 429 错误时，等待 1 秒后重试，再失败等待 2 秒、4 秒、8 秒……
    而不是立即重试。
  </Step>
</Steps>

## 单次请求大小限制

| 限制项 | 说明 |
|-------|------|
| 请求体大小 | 单次请求的总大小有上限，通常包含输入和输出 |
| 输入 Token | 单次请求的输入（prompt）Token 数受模型上下文窗口限制 |
| 输出 Token | `max_tokens` 参数不能超过模型允许的最大值 |

如果你发送大量文本作为上下文，可能触发以下错误：

- `context_length_exceeded` — 输入超过模型的上下文窗口
- `payload_too_large` — 请求体超过平台限制

### 建议

- 长文本请分段处理，不要一次性发送整个文档
- 使用摘要或向量检索减少上下文长度
- 设置合理的 `max_tokens`，避免等待过长响应

## 并发限制

同一用户的同时进行中的请求数有上限。如果你使用多线程或异步方式调用 API：

- 建议并发数不超过 **3-5**
- 并发过高会被网关拒绝，返回 429 错误
- 流式请求在完成前持续占用并发槽位

## 每日额度

每个用户每天有 Token 消耗上限，这是公益站最核心的限制。

<Callout type="info" title="额度如何计算">
  额度按 Token 折算。不同模型的消耗比例不同：
  - GPT-4 系列消耗快，单次对话可能用掉当天大部分额度
  - GPT-3.5 / DeepSeek 等模型消耗慢，可以进行更多次调用
  - 具体倍率可能在控制台的模型价格页面查看
</Callout>

额度耗尽时你会收到 `insufficient_quota` 错误。额度在每天固定时间重置。

## 常见错误一览

| 错误码 | 含义 | 解决方法 |
|-------|------|---------|
| 401 | API Key 无效或已过期 | 检查令牌是否正确、是否已禁用 |
| 403 | 无权访问该模型 | 检查令牌是否限制了模型范围 |
| 429 | 请求过频或额度不足 | 降低频率或等待次日额度刷新 |
| 500 | 服务器内部错误 | 稍后重试 |
| 502 / 503 | 上游服务商不可用 | 换一个模型或稍后重试 |
| 504 | 请求超时 | 检查输入是否过大，或重试 |

## 合理使用建议

<Callout type="info" title="做一个好用户">
  公益站资源有限，合理使用让所有人都能受益。
</Callout>

- ✅ 用于学习、实验、个人项目
- ✅ 控制调用频率，不并发刷量
- ✅ 用国产模型做日常测试，省下额度给关键调用
- ✅ 遇到问题先查文档再问
- ❌ 不要用于商业服务或线上产品
- ❌ 不要搭建转发代理二次转售
- ❌ 不要用脚本无限制轮询
- ❌ 不要在请求中发送敏感数据
